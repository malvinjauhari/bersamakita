2. RINGKASAN TECHNOLOGY APPROACH
--------------------------------------------------------------------------------
Platform Bersama Kita dirancang untuk memecahkan tiga kendala kritis dalam
penyaluran bantuan bencana di Indonesia:
  (1) Kesimpangsiuran data bencana sebelum verifikasi resmi lapangan.
  (2) Ketidakjelasan pemotongan biaya transaksi donasi digital.
  (3) Minimnya transparansi penyaluran dana hingga ke mitra relawan posko.

Untuk menjawab kebutuhan tersebut dalam konteks pengembangan produk hackathon
nasional, pendekatan teknologi yang diterapkan mengusung prinsip "Lean, Decoupled,
and Authoritative Integrity":

  a. Frontend Modern Berkinerja Tinggi:
     Menggunakan React 19, TypeScript, Tailwind CSS v4, dan React Router v7
     yang dibundel oleh Vite 8. Seluruh antarmuka bersifat deklaratif, responsif,
     dan bebas dependensi berat pihak ketiga (seperti Google Maps / Leaflet SDK)
     dengan mengimplementasikan peta seismik interaktif berbasis Custom SVG
     Web Mercator berukuran ringan (<70 KB).

  b. Backend Hybrid & Proxy Aman:
     Menggunakan Express 4 di atas Node.js 22 yang dapat berjalan sebagai server
     lokal terintegrasi (dengan Vite middleware) maupun dideploy sebagai Serverless
     Function di Vercel. Backend bertindak sebagai proxy aman untuk API BMKG
     (mengatasi hambatan CORS), penerbit signature unggah gambar Cloudinary,
     pengelola webhook Duitku, serta agregator transparansi finansial server-side.

  c. Database & Otentikasi Terisolasi:
     Memadukan Firebase Authentication untuk manajemen identitas donatur (Google
     OAuth) dan staf (Email/Password), dengan Cloud Firestore sebagai NoSQL data
     store yang diproteksi aturan keamanan berbasis baris (Row-Level Security pada
     firestore.rules). Backend Express memanfaatkan Firebase Admin SDK untuk
     menjalankan operasi administratif atomik (batch writes dan database transactions).

  d. Gateway Pembayaran Terstandarisasi & Transparan:
     Mengadopsi Duitku Direct API secara eksklusif untuk metode pembayaran QRIS
     (ShopeePay QRIS / kode 'SP'). Seluruh biaya administrasi dihitung transparan
     (0,17% flat) dan dipisahkan dari dana donasi pokok. Konfirmasi pembayaran
     dilindungi validasi HMAC-SHA256 dan logika idempoten mutlak.


3. GAMBARAN UMUM SISTEM
--------------------------------------------------------------------------------
Bersama Kita menghubungkan empat entitas utama dalam satu ekosistem tanggap darurat:

  1. Donatur Publik:
     Melihat posko bencana terverifikasi, membaca analisis situasi dampak seismik,
     melakukan donasi via scan QRIS tanpa popup berbelit, memantau riwayat donasi
     pribadi, dan melacak pergerakan bantuan secara kolektif per bencana.

  2. Administrator Operasional:
     Menerima data gempa bumi mentah dari BMKG ke dalam antrean pending, menugaskan
     Mitra Lapangan resmi (misal: PMI, BAZNAS), menyetujui aktivasi posko bencana,
     mengajukan pencairan dana operasional (disbursement) dengan validasi saldo
     otomatis server-side, dan mengelola akun staf mitra.

  3. Mitra Lapangan (Field Partner):
     Menerima alokasi dana bantuan, memperbarui tahapan distribusi bertahap (dana
     masuk kas posko -> bantuan dikemas -> logistik berangkat -> tiba di posko ->
     serah terima warga -> tuntas 100%), dan mengunggah foto bukti real-time.

  4. Layanan Eksternal Terintegrasi:
     - BMKG Open Data: Sumber data seismik realtime nasional.
     - Duitku Payment Gateway: Pemroses invoice dan webhook pembayaran QRIS.
     - Cloudinary: Penyimpanan bukti foto distribusi dan logo mitra.
     - Vercel: Infrastruktur hosting frontend dan serverless execution.

5. ANALISIS TEKNOLOGI DAN ALASAN PEMILIHAN
--------------------------------------------------------------------------------

A. FRONTEND LAYER

1. React (v19.0.1) & React DOM (v19.0.1)
   - Kategori          : Frontend Library / UI Framework
   - Status            : IMPLEMENTED
   - Fungsi            : Mengelola hierarki komponen antarmuka, rendering deklaratif,
                         dan sinkronisasi state lokal pengguna di seluruh alur donasi.
   - Bukti             : package.json (baris 30-31), src/main.tsx, src/App.tsx.
   - Alasan Pemilihan  : React 19 menawarkan efisiensi lifecycle dan kompatibilitas
                         tinggi dengan ekosistem pustaka modern. Pendekatan berbasis
                         komponen sangat ideal untuk memisahkan fitur donasi,
                         dasbor bencana, dan portal verifikasi admin secara modular.
   - Alternatif        : Vue.js, Svelte, Next.js.
   - Mengapa Terpilih  : Proyek membutuhkan SPA murni dengan kontrol rendering penuh
                         yang dapat di-bundle secara ringan tanpa overhead server
                         kompleks milik framework fullstack berorientasi SSR.
   - Kelebihan         : Ekosistem sangat kaya, reusabilitas komponen tinggi.
   - Keterbatasan      : Manajemen re-render membutuhkan kehati-hatian pada memoization.
   - Risiko & Mitigasi : Kinerja melambat jika tree komponen terlalu dalam.
                         Mitigasi: Memecah view per-fitur (features/*) dan membatasi scope state.

2. TypeScript (v7.0.2 / Engine Types v19 & v22)
   - Kategori          : Programming Language
   - Status            : IMPLEMENTED
   - Fungsi            : Menetapkan kontrak tipe data yang ketat (interface Disaster,
                         Donation, PaymentRecord, Disbursement, dll) serta menjamin
                         type-safety antar file.
   - Bukti             : tsconfig.json, src/types/index.ts, package.json (baris 45).
   - Alasan Pemilihan  : Menghindari runtime bug klasik JavaScript (seperti undefined
                         property access) terutama saat memproses kalkulasi nominal
                         keuangan donasi dan data respons API eksternal.
   - Alternatif        : Vanilla JavaScript, JSDoc.
   - Mengapa Terpilih  : Dalam sistem keuangan dan kebencanaan, integritas tipe data
                         merupakan syarat mutlak untuk mencegah kesalahan nominal transaksi.
   - Kelebihan         : Deteksi error saat pengetikan kode (compile-time), refactoring aman.
   - Keterbatasan      : Membutuhkan waktu tambahan untuk merumuskan kontrak tipe data.
   - Risiko & Mitigasi : Penggunaan tipe `any` yang meloloskan bug.
                         Mitigasi: Pengecekan rutin via `npm run lint` (`tsc --noEmit`).

3. Vite (v8.3.0) & @vitejs/plugin-react (v6.1.1)
   - Kategori          : Build Tool & Dev Server
   - Status            : IMPLEMENTED
   - Fungsi            : Menyediakan dev server dengan Hot Module Replacement (HMR)
                         instan serta membundel aset produksi ke direktori `dist`.
                         Diintegrasikan pula sebagai Express middleware pada mode development.
   - Bukti             : vite.config.ts, package.json (baris 23, 34), server/app.ts (baris 43-48).
   - Alasan Pemilihan  : Waktu build dan cold-start jauh lebih cepat dibanding Webpack
                         berkat pemanfaatan native ES Modules dan esbuild.
   - Alternatif        : Webpack, Create React App (deprecated), Turbopack.
   - Mengapa Terpilih  : Kecepatan iterasi merupakan kunci keberhasilan proyek dalam
                         lingkungan kompetisi hackathon yang serba cepat.
   - Kelebihan         : Startup instan, build bundle produksi sangat teroptimasi.
   - Keterbatasan      : Konfigurasi manual diperlukan saat dipasangkan dengan custom Express server.
   - Risiko & Mitigasi : Perbedaan perilaku environment lokal vs Vercel serverless.
                         Mitigasi: Konfigurasi rewrites eksplisit di vercel.json.

4. Tailwind CSS (v4.3.3) & @tailwindcss/vite (v4.3.3)
   - Kategori          : Styling Engine
   - Status            : IMPLEMENTED
   - Fungsi            : Mengatur seluruh tata letak visual, tema warna (#0C8F63, #1B3322),
                         tipografi, dan responsivitas UI menggunakan utility classes.
   - Bukti             : src/index.css (baris 1: `@import "tailwindcss";`), vite.config.ts (baris 1, 8).
   - Alasan Pemilihan  : Tailwind CSS v4 menggunakan engine Oxide berbasis Rust yang
                         meniadakan konfigurasi JavaScript terpisah, menghasilkan waktu
                         kompilasi instan dan bundle CSS minimal.
   - Alternatif        : Tailwind v3, CSS Modules, Styled Components.
   - Mengapa Terpilih  : Kemudahan prototyping UI bertaraf premium tanpa menulis CSS manual
                         yang rawan redundansi.
   - Kelebihan         : Kecepatan styling tinggi, zero config file, tree-shaking otomatis.
   - Keterbatasan      : Kerapatan utility class pada tag JSX jika tidak dipecah komponen.
   - Risiko & Mitigasi : Desain tidak seragam.
                         Mitigasi: Memusatkan token warna dan styling tombol pada class utilitas bersama.

5. Custom SVG Interactive Map (Web Mercator Projection)
   - Kategori          : GIS / Vector Visualization Component
   - Status            : IMPLEMENTED
   - Fungsi            : Menampilkan peta geografis wilayah kepulauan Indonesia secara
                         interaktif dengan kemampuan pan, wheel-zoom, pinch-to-zoom,
                         animasi `flyTo` ke titik koordinat gempa, serta penanda status posko.
   - Bukti             : src/features/disaster/EarthquakeMap.tsx,
                         src/features/disaster/data/indonesiaMap.ts,
                         scripts/generate-indonesia-map.mjs.
   - Alasan Pemilihan  : Dibangun dari data Natural Earth 50m resolusi admin-1.
                         Menghilangkan kebutuhan API Key pihak ketiga (Google Maps / Mapbox
                         yang membutuhkan billing aktif dan rawan habis kuota) serta
                         menghindari beban unduh tile map bitmap yang berat.
   - Alternatif        : Leaflet.js, Mapbox GL JS, Google Maps JavaScript API.
   - Mengapa Terpilih  : Ukuran bundle sangat ringkas (<70 KB data vektor terkompresi),
                         bebas kuota / rate limit, 100% offline-friendly, dan dapat di-style
                         sepenuhnya menyatu dengan tema visual aplikasi.
   - Kelebihan         : 0 biaya operasional API, performa animasi 60 fps stabil, privasi data aman.
   - Keterbatasan      : Tidak memiliki detail jalan setapak (street-level) perkotaan.
   - Risiko & Mitigasi : Kesalahan proyeksi titik koordinat gempa BMKG.
                         Mitigasi: Fungsi proyeksi matematis Web Mercator formal pada `project(lng, lat)`.


B. BACKEND & RUNTIME LAYER

1. Node.js (v22.x LTS) & Express (v4.21.2)
   - Kategori          : Backend Runtime & Web Server
   - Status            : IMPLEMENTED
   - Fungsi            : Menyediakan REST API backend, menerima webhook Duitku, mem-proxy
                         data BMKG tanpa CORS, memvalidasi Firebase ID Token staf, dan
                         mengagregasi data transparansi keuangan.
   - Bukti             : package.json (baris 7, 25), server/app.ts, server/routes/*.ts.
   - Alasan Pemilihan  : Node.js 22 LTS memiliki kestabilan runtime tinggi dan dukungan
                         `fetch` native. Express menyediakan middleware modular yang
                         sangat mudah dipasangkan dengan Vercel Serverless Function.
   - Alternatif        : Fastify, NestJS, Go (Fiber/Gin).
   - Mengapa Terpilih  : Kemudahan berbagi interface TypeScript (`src/types`) dan logika
                         kalkulasi fee (`src/lib/fees.ts`) antara frontend dan backend
                         dalam satu repositori (unified codebase).
   - Kelebihan         : Waktu setup cepat, footprint memori rendah, fleksibel.
   - Keterbatasan      : Tidak memiliki sistem injeksi dependensi bawaan (arsitektur
                         bergantung pada kedisiplinan pembagian folder router).
   - Risiko & Mitigasi : Penanganan rute yang tidak sinkron dapat mengembalikan HTML 404.
                         Mitigasi: JSON 404 handler eksplisit di `api/index.ts` untuk
                         menjamin semua rute `/api/*` selalu mengembalikan JSON.

2. tsx (v4.21.0)
   - Kategori          : TypeScript Runtime Engine
   - Status            : IMPLEMENTED
   - Fungsi            : Menjalankan file TypeScript server (`server/app.ts`) secara langsung
                         baik pada mode dev maupun mode start produksi tanpa build step perantara.
   - Bukti             : package.json (baris 13, 15, 33).
   - Alasan Pemilihan  : Berbasis esbuild, mengeksekusi berkas TypeScript dalam hitungan milidetik,
                         mendukung konfigurasi ESM murni.
   - Alternatif        : ts-node, manual build via tsc.
   - Mengapa Terpilih  : Mengeliminasi lag kompilasi yang sering terjadi pada `ts-node`.
   - Kelebihan         : Cepat, konfigurasi nol, kompatibel dengan Node ESM.
   - Keterbatasan      : Tidak melakukan verifikasi tipe data saat runtime.
   - Risiko & Mitigasi : Potensi error ketidaksesuaian tipe saat server berjalan.
                         Mitigasi: Skrip `npm run lint` dijalankan sebelum deploy.


C. DATABASE, AUTHENTICATION, & STORAGE LAYER

1. Cloud Firestore (Client SDK v12.19.0 & Admin SDK v14.5.0)
   - Kategori          : NoSQL Document Database
   - Status            : IMPLEMENTED
   - Fungsi            : Menyimpan seluruh entitas platform: bencana, donasi, pembayaran,
                         pencairan, data mitra, alokasi, laporan lapangan, dan log audit.
   - Bukti             : src/config/firebase.ts, src/config/firebase-admin.ts,
                         src/services/firebase/firestore.ts, firestore.rules.
   - Alasan Pemilihan  : Skalabilitas tinggi berbasis cloud terkelola (fully managed serverless),
                         kecepatan query real-time, integrasi langsung dengan Firebase Auth.
   - Alternatif        : PostgreSQL / Supabase, MongoDB Atlas.
   - Mengapa Terpilih  : Kemudahan aturan keamanan tingkat dokumen (Row-Level Security)
                         langsung di level database melalui `firestore.rules`.
   - Kelebihan         : Zero server maintenance, query cepat, transaksi atomik terjamin.
   - Keterbatasan      : Query majemuk membutuhkan definisi composite index manual.
   - Risiko & Mitigasi : Field `undefined` menyebabkan penolakan write oleh Firestore SDK.
                         Mitigasi: Pembersihan rekursif menggunakan fungsi utilitas
                         `sanitizeForFirestore()` sebelum dokumen disimpan.

2. Firebase Authentication (Client SDK v12.19.0 & Admin SDK v14.5.0)
   - Kategori          : Identity & Access Management
   - Status            : IMPLEMENTED
   - Fungsi            : Mengelola otentikasi donatur melalui Google Sign-In dan staf
                         (Admin/Mitra) melalui kredensial terdaftar. Backend memverifikasi
                         keabsahan JWT ID token via `adminAuth.verifyIdToken()`.
   - Bukti             : src/services/firebase/auth.ts, src/features/auth/AuthContext.tsx,
                         server/routes/admin.ts, server/routes/fundraising.ts.
   - Alasan Pemilihan  : Standar industri manajemen otentikasi Google tanpa perlu menyimpan
                         password hash mentah di database sendiri.
   - Alternatif        : Custom JWT manual, Auth0, Supabase Auth.
   - Mengapa Terpilih  : Ekosistem terintegrasi dengan Firebase Rules sehingga `request.auth`
                         dapat langsung diakses pada aturan keamanan Firestore.
   - Kelebihan         : Keamanan kelas enterprise, proteksi brute-force bawaan.
   - Keterbatasan      : Domain OAuth harus didaftarkan di Firebase Console.
   - Risiko & Mitigasi : Kegagalan otentikasi pihak ketiga saat jaringan lambat.
                         Mitigasi: Mekanisme fallback profil lokal pada `auth.ts`.

3. Cloudinary (Direct Signed Upload REST API)
   - Kategori          : Media & Image Cloud Storage
   - Status            : IMPLEMENTED
   - Fungsi            : Menampung foto dokumentasi penyaluran bantuan logistik lapangan,
                         foto bukti serah terima, dan logo profil mitra.
   - Bukti             : server/routes/images.ts, src/services/cloudinary.ts,
                         src/components/ImageUploadField.tsx.
   - Alasan Pemilihan  : Beban pengunggahan gambar dialihkan langsung dari peramban ke CDN
                         Cloudinary tanpa membebani bandwidth dan memori server Express.
                         Kredensial rahasia (`CLOUDINARY_API_SECRET`) tetap terjaga di server
                         karena backend hanya menerbitkan SHA-1 signature berdurasi singkat.
   - Alternatif        : Firebase Storage, AWS S3.
   - Mengapa Terpilih  : Cloudinary menyediakan optimasi gambar otomatis (WebP/format delivery)
                         dan implementasi signed upload yang sangat aman.
   - Kelebihan         : Server Express tidak terbebani file biner besar, CDN global cepat.
   - Keterbatasan      : Kuota penyimpanan gratis memiliki batas kredit bulanan.
   - Risiko & Mitigasi : Upload file berbahaya atau format ilegal.
                         Mitigasi: Validasi ganda tipe file (JPEG/PNG/WEBP, maks 5 MB) di
                         sisi client dan folder whitelist di sisi server.


D. INTEGRASI EXTERNAL & PAYMENT GATEWAY LAYER

1. Duitku Direct API (QRIS Code: 'SP')
   - Kategori          : Payment Gateway
   - Status            : IMPLEMENTED
   - Fungsi            : Menghasilkan invoice QRIS resmi, menerima notifikasi webhook status
                         pembayaran, dan menyediakan endpoint pemeriksaan status transaksi.
   - Bukti             : server/routes/payments.ts, src/services/duitku.ts,
                         src/features/donation/TransactionCheckoutPage.tsx.
   - Alasan Pemilihan  : QRIS adalah standar transaksi nontunai nasional Indonesia yang
                         didukung seluruh e-wallet dan mobile banking. Direct API
                         memungkinkan rendering payload QR code langsung di dalam halaman
                         aplikasi tanpa modal pop-up yang kerap terblokir pop-up blocker.
   - Alternatif        : Midtrans, Xendit, Duitku POP (Iframe).
   - Mengapa Terpilih  : Kerapihan UX — donatur tetap berada di halaman platform dan
                         mendapatkan kepastian perhitungan biaya administrasi transparan.
   - Kelebihan         : Protokol keamanan kuat (MD5 inquiry + HMAC-SHA256 callback).
   - Keterbatasan      : Waktu kedaluwarsa QRIS harus disinkronkan dengan timer frontend.
   - Risiko & Mitigasi : Notifikasi webhook terkirim ganda atau tertunda.
                         Mitigasi: Logika callback idempoten mutlak di backend dan
                         fitur polling sinkronisasi manual (`check-status`).

2. BMKG Open Data (TEWS API)
   - Kategori          : External Disaster Data Source
   - Status            : IMPLEMENTED
   - Fungsi            : Mengambil data resmi guncangan gempa bumi terkini di Indonesia.
   - Bukti             : server/routes/bmkg.ts, src/services/bmkg.ts.
   - Alasan Pemilihan  : Otoritas pemerintah tunggal yang sah untuk data kegempaan nasional.
   - Alternatif        : USGS, EMSC.
   - Mengapa Terpilih  : Data wilayah disajikan dalam konteks penamaan geografis Indonesia.
   - Kelebihan         : Data publik tanpa keharusan token otorisasi rahasia.
   - Keterbatasan      : BMKG tidak mengizinkan akses Cross-Origin Resource Sharing (CORS).
   - Risiko & Mitigasi : Request diblokir oleh browser.
                         Mitigasi: Seluruh pengambilan data dialihkan melalui backend proxy
                         Express dengan timeout 8 detik dan status fallback terisolasi.


6. ARSITEKTUR SISTEM
--------------------------------------------------------------------------------

Arsitektur sistem Bersama Kita memisahkan domain publik dan operasional secara tegas:

```
[ KLIEN & PENGGUNA ]
  │
  ├── Donatur Publik (Guest / Google Auth) ───┐
  ├── Administrator Operasional (Email Auth) ─┼──> [ FRONTEND: React 19 + Vite 8 ]
  └── Mitra Lapangan (Email Auth) ────────────┘       (SPA Client Routing, SVG Map)
                                                             │           │
                     ┌───────────────────────────────────────┘           │
                     │ (Kueri Data Langsung via Firebase Client SDK)     │ (HTTP Proxy,
                     │  Diproteksi firestore.rules                       │  Upload Sign,
                     ▼                                                   │  Payment API)
        [ FIREBASE INFRASTRUCTURE ]                                      ▼
        ├── Firebase Auth (Identity Management)             [ BACKEND: Express 4 on Node 22 ]
        └── Cloud Firestore (NoSQL Document Store)          ├── /api/bmkg/*  (CORS Proxy)
              ▲                                             ├── /api/payments/duitku/* (Payment)
              │ (Administrative Writes & Batch Mutasi)      ├── /api/images/sign (Cloudinary)
              │ Menggunakan Firebase Admin SDK              ├── /api/transparency/* (Public Data)
              │                                             └── /api/fundraising/* (Disbursement)
              │                                                        │       │       │
              └────────────────────────────────────────────────────────┘       │       │
                                                                               │       │
           ┌───────────────────────────────────────────────────────────────────┘       │
           ▼                                                                           ▼
   [ Duitku Payment Gateway ]                                           [ BMKG Open Data TEWS ]
   - Inquiry API (MD5)                                                  - autogempa.json
   - Status Check API (HMAC-SHA256)                                     - gempaterkini.json
   - Webhook Callback Receiver (HMAC-SHA256)                            (8s timeout, User-Agent)
```

PEMISAHAN TANGGUNG JAWAB (SEPARATION OF CONCERNS):
1. Frontend (React + Vite):
   - Bertanggung jawab murni atas penyajian UI, interaksi peta, formulir donasi,
     dan render state.
   - Membaca data publik/privat langsung dari Firestore dengan pengamanan `firestore.rules`.
   - Tidak pernah menyimpan secret key backend atau memutasi status pembayaran secara mandiri.

2. Backend (Express Server):
   - Bertindak sebagai integration hub dan security gateway.
   - Mengelola komunikasi berlisensi rahasia (Duitku API Key, Cloudinary Secret, Service Account).
   - Menjalankan proxy data BMKG guna menembus batasan CORS browser.
   - Menjalankan mutasi sensitif (update donasi 'paid', penugasan mitra, pembuatan akun mitra).

3. Database (Cloud Firestore):
   - Menjadi Single Source of Truth status data platform.
   - Menerapkan Row-Level Security: donatur hanya dapat membaca donasi miliknya sendiri,
     sedangkan laporan distribusi yang berstatus 'published' dapat diakses oleh publik.


7. INTEGRASI ANTAR-LAYANAN
--------------------------------------------------------------------------------

A. ALUR PENGAMBILAN & VERIFIKASI BENCANA (BMKG TO ACTIVE)
   Aturan Bisnis Permanen: Data BMKG tidak boleh tampil otomatis ke publik.
   Status sebelum verifikasi harus EMPTY STATE. Tidak ada auto-approval 24 jam.

   1. Penarikan Data:
      Frontend (atau Admin) memicu pembaruan seismik -> request dikirim ke backend
      `/api/bmkg/autogempa` dan `/api/bmkg/gempaterkini`. Backend memanggil endpoint BMKG
      dengan User-Agent khusus dan timeout 8 detik.
   2. Penyimpanan Awal:
      Data yang dinormalisasi disimpan ke koleksi `disasters` dengan status wajib:
      `status = 'pending_verification'` dan `verificationMethod = 'pending'`.
   3. Peninjauan & Penugasan Mitra:
      Admin membuka antrean verifikasi di Admin Dashboard. Admin WAJIB memilih Mitra
      Lapangan (Partner) aktif yang bertugas di wilayah tersebut sebelum menyetujui.
   4. Persetujuan Eksplisit:
      Admin mengklik "Approve Bencana". Status diperbarui menjadi `admin_approved`.
   5. Tampil ke Donatur:
      Kueri publik hanya mengambil data bencana berstatus `admin_approved`.
      Sebelum ada bencana yang disetujui, donatur melihat tampilan Empty State resmi.

B. ALUR PEMBAYARAN DONASI (DUITKU QRIS)
   Aturan Bisnis Permanen: QRIS adalah satu-satunya metode aktif. Biaya admin 0,17% transparan.

   1. Inisiasi Donasi:
      Donatur memilih posko bencana di `/transaction/donate/:disasterId`, mengisi
      nominal donasi (minimal Rp10.000), nama, dan email.
   2. Pembuatan Invoice di Backend:
      Frontend memanggil `POST /api/payments/duitku/create`.
      Backend menghitung biaya admin server-side (`src/lib/fees.ts`):
        Biaya Admin   = Nominal × 0,17%
        Total Dibayar = Nominal + Biaya Admin
      Backend membuat signature MD5 (`merchantCode + merchantOrderId + paymentAmount + apiKey`)
      dan mengirimkan inquiry ke server Duitku dengan kode `paymentMethod: 'SP'`.
   3. Penyajian QRIS:
      Duitku mengembalikan payload string QRIS (`qrString`). Backend menyimpan dokumen
      pembayaran awal di Firestore (`status: 'pending'`). Frontend merender QRIS
      menggunakan engine render SVG/canvas pada `/transaction/checkout/:donationId`.
   4. Webhook Callback Duitku:
      Ketika donatur memindai dan membayar, server Duitku mengirim HTTP POST ke
      `/api/payments/duitku/callback`.
      Backend memvalidasi signature HMAC-SHA256 (`merchantCode + amount + merchantOrderId`).
      Jika signature valid dan `resultCode === '00'`:
        - Dilakukan pemeriksaan idempoten: jika status sudah `paid`, respons langsung sukses.
        - Jika status masih `pending`, batch mutasi Firebase Admin SDK memperbarui
          `payments` -> `paid`, `donations` -> `paid`, dan menyisipkan event
          `trackingEvents` ("Dana Donasi Diterima").
   5. Redirection & Polling:
      Halaman checkout memantau status via `/api/payments/duitku/check-status`.
      Setelah terkonfirmasi, donatur dialihkan ke `/transaction/status/:donationId`.

C. ALUR PENCAIRAN DANA (DISBURSEMENT) & PELAPORAN DISTRIBUSI
   1. Validasi Saldo Server-Side:
      Admin mengajukan pencairan via `POST /api/fundraising/admin/disbursements`.
      Backend menghitung saldo kas nyata dari total donasi berstatus `paid` dikurangi
      pencairan sebelumnya. Klien tidak dapat memanipulasi nominal saldo.
   2. Transaksi Atomik:
      Secara atomik, backend mencatat dokumen `disbursements`, dokumen `partnerAllocations`,
      log audit, dan memperbarui `disasterTimeline` kolektif bencana.
   3. Konfirmasi & Pelaporan Mitra:
      Mitra Lapangan membuka Partner Dashboard, mengonfirmasi penerimaan dana kas,
      lalu memperbarui progres bertahap (barang dikemas, armada berangkat, serah terima).
   4. Bukti Foto Terverifikasi:
      Foto dokumentasi diunggah ke Cloudinary via endpoint penandatangan `/api/images/sign`.
      Dokumen `distributionReports` diterbitkan sehingga dapat diakses publik pada
      halaman Transparansi Penyaluran.


8. PERTIMBANGAN KEAMANAN DAN INTEGRITAS DATA
--------------------------------------------------------------------------------

1. Manajemen Secret & Isolasi Variabel Lingkungan:
   - Variabel rahasia (`DUITKU_API_KEY`, `FIREBASE_SERVICE_ACCOUNT_JSON`,
     `CLOUDINARY_API_SECRET`, `ADMIN_SECRET_KEY`, `CRON_SECRET`) tidak memiliki
     prefix `VITE_` dan hanya dimuat di lingkungan backend Node.js.
   - Bundler Vite menjamin bahwa variabel tanpa prefix `VITE_` tidak akan pernah
     terekspos ke dalam berkas JavaScript klien.

2. Kontrol Akses Database (Firestore Security Rules):
   - Aturan default deny diterapkan pada root database (`allow read, write: if false`).
   - Isolasi data donatur: Donatur hanya dapat membaca dan memperbarui data donasi
     yang memiliki `userId` sesuai dengan UID token login miliknya.
   - Isolasi peran staf: Fungsi pembantu `isAdmin()` dan `isPartner()` memverifikasi
     identitas token otentikasi terhadap dokumen pengguna di koleksi `users`.
   - Bencana mentah BMKG yang berstatus `pending_verification` diblokir dari pembacaan
     publik dan hanya dapat diakses oleh Admin dan Mitra.

3. Integritas Pembayaran & Anti-Tampering:
   - Klien tidak diberikan wewenang untuk mengubah status donasi menjadi 'paid' secara langsung.
   - Webhook Duitku divalidasi ketat menggunakan hashing kriptografi HMAC-SHA256.
   - Sifat idempoten pada handler callback menjamin bahwa pengiriman webhook berulang
     kali oleh jaringan gateway tidak akan pernah menggandakan pencatatan dana donasi.

4. Integritas Transaksi Kas & Alokasi:
   - Pencairan dana operasional dieksekusi menggunakan `db.runTransaction()` pada
     Firebase Admin SDK untuk mencegah kondisi race condition (double spending).
   - Batas maksimum penarikan dikunci secara matematis di server menggunakan utilitas
     `maxWithdrawableAmount()` yang memperhitungkan biaya administrasi pencairan.

5. Sanitasi Data:
   - Seluruh penulisan dokumen ke Firestore melalui fungsi `sanitizeForFirestore()`
     guna menghapus properti bernilai `undefined` yang berpotensi memicu error crash SDK.


9. KELEBIHAN DAN KETERBATASAN TECHNOLOGY STACK
--------------------------------------------------------------------------------

KELEBIHAN:
  1. Kecepatan & Kelincahan Pengembangan (Rapid Hackathon Execution):
     Penggunaan stack TypeScript terpadu (React + Express) mempercepat pembagian
     kontrak data dan logika bisnis antar tier tanpa proses konversi tipe.
  2. Bebas Biaya Layanan Peta Eksternal:
     Peta kustom SVG Web Mercator menghilangkan risiko penangguhan akun akibat
     kuota API peta komersial yang habis saat pengujian demo juri.
  3. Keamanan Tingkat Transaksi Tinggi:
     Kombinasi Direct API Duitku, signature cryptographic validation, dan
     Firestore Row-Level Security memberikan jaminan keamanan data yang solid.
  4. Efisiensi Biaya Infrastruktur:
     Model arsitektur serverless di Vercel dan Firebase meminimalkan biaya hosting
     tetap (zero idle cost).
  5. UI/UX Responsif dan Ringan:
     Waktu muat awal sangat cepat karena ketiadaan library pemetaan bitmap yang masif.

KETERBATASAN:
  1. Ketergantungan Kuota Cloudinary & Firebase Gratis:
     Jika pengujian donasi dan unggah media dalam skala ribuan dilakukan secara simultan,
     limit frekuensi Spark Plan Firebase dan kredit Cloudinary dapat tercapai.
  2. Ketiadaan Full GIS Layer pada Peta:
     Peta SVG in-house difokuskan pada tingkat provinsi dan titik episentrum gempa,
     belum mendukung layer jalan mikro atau citra satelit resolusi tinggi.
  3. Serverless Cold Start:
     Pada platform Vercel, inisialisasi awal serverless function membutuhkan waktu
     sekitar 1-2 detik jika tidak ada request yang masuk dalam jangka waktu tertentu.
  4. Ketiadaan Database Relasional Terstruktur:
     Agregasi data keuangan (seperti total penerimaan pada `/api/fundraising/summary`)
     dilakukan secara komputasi di memori server dari dokumen Firestore, yang
     memerlukan refaktorisasi ke distributed counter jika volume transaksi melebihi
     ratusan ribu dokumen.


10. RISIKO TEKNIS DAN MITIGASI
--------------------------------------------------------------------------------

1. Risiko: Kegagalan Jaringan atau Down-time Server BMKG
   - Deskripsi : API BMKG sewaktu-waktu mengalami lonjakan beban saat terjadi gempa besar,
                 berpotensi menyebabkan request gantung (hanging request).
   - Mitigasi  : Backend menerapkan `AbortSignal.timeout(8000)`. Jika BMKG tidak merespons
                 dalam 8 detik, server mengembalikan status 502 tanpa menghentikan
                 aplikasi utama. Data yang berhasil diambil sebelumnya tetap tersimpan
                 aman di Firestore.

2. Risiko: Callback Webhook Pembayaran Tidak Sampai (Network Partition)
   - Deskripsi : Gangguan rute jaringan internet dapat menyebabkan webhook dari Duitku
                 gagal mencapai endpoint callback backend.
   - Mitigasi  : Disediakan endpoint aktif `POST /api/payments/duitku/check-status` yang
                 dapat dipanggil oleh klien untuk mengonfirmasi status ke server Duitku,
                 ditambah cron job harian (`expire-sweep`) yang memeriksa status transaksi tertunda.

3. Risiko: Kebocoran Data Donasi Antar Donatur
   - Deskripsi : Donatur A dapat melihat riwayat donasi Donatur B jika kueri database tidak terisolasi.
   - Mitigasi  : `firestore.rules` menerapkan isolasi ketat `request.auth.uid == userId`.
                 Kueri frontend `getUserDonations` mengunci pencarian hanya pada UID aktif.

4. Risiko: Penarikan Dana Melebihi Saldo Kas (Overdraft)
   - Deskripsi : Admin mengajukan pencairan dana melebihi sisa dana riil yang terkumpul.
   - Mitigasi  : Endpoint `/api/fundraising/admin/disbursements` menghitung sisa kas
                 riil secara real-time di server via Admin SDK sebelum menjalankan transaksi atomik.

12. KESIMPULAN TECHNOLOGY APPROACH
--------------------------------------------------------------------------------
Dokumen ini menyajikan kesimpulan kelayakan teknis yang siap disadur langsung ke
dalam naskah Proposal Hackathon Nasional:

1. Mengapa Stack Ini Sesuai dengan Kebutuhan Produk?
   Kombinasi React 19, Express, Firebase Firestore, dan Duitku Direct API QRIS
   sangat tepat karena memecahkan kebutuhan inti platform donasi bencana:
   kecepatan penyajian informasi, transparansi mutlak, dan keamanan transaksi keuangan.
   Pilihan arsitektur ini memisahkan kueri publik yang cepat dari mutasi finansial
   yang membutuhkan otoritas server-side.

2. Bagaimana Komponen Teknologi Mendukung Fitur Inti?
   - Fitur Posko Bencana: Didukung oleh proxy BMKG aman, verifikasi wajib Admin,
     dan peta interaktif SVG berkinerja tinggi.
   - Fitur Donasi Tanpa Hambatan: Didukung oleh Duitku QRIS Direct API yang
     mengeliminasi popup serta menampilkan rincian biaya admin 0,17% secara transparan.
   - Fitur Transparansi Penyaluran: Didukung oleh agregasi server-side Firebase Admin SDK,
     tahapan milestone distribusi mitra, dan bukti foto Cloudinary.

3. Apakah Arsitektur Cukup Realistis dalam Durasi Hackathon?
   Sangat realistis. Struktur codebase telah terbukti modular dan berfungsi secara
   terpadu (unified repository). Tidak ada over-engineering arsitektur microservices
   yang membebani pengujian, dan seluruh komponen utama telah diuji interoperabilitasnya.

4. Apa Keterbatasan Teknis Paling Penting?
   Ketergantungan database pada pembacaan dokumen NoSQL (Firestore) yang memerlukan
   agregasi berbasis loop memori di backend. Hal ini sangat memadai untuk skala demo
   dan tahap awal produk (hingga puluhan ribu transaksi), namun membutuhkan database
   relasional atau Cloud Functions aggregator untuk skala produksi nasional masif.

5. Rekomendasi Sebelum Sesi Demonstrasi Produk (Demo Pitching):
   - Melakukan uji coba transaksi simulasi Duitku Sandbox untuk memastikan webhook
     berhasil memutasi status donasi menjadi 'paid' secara instan.
   - Menghapus tag script legacy Duitku POP dari `index.html` agar tidak memuat library
     eksternal yang tidak diperlukan.
   - Menjelaskan secara jujur kepada dewan juri bahwa fitur analisis dampak saat ini
     menggunakan Rule-Based Heuristic seismik resmi BMKG, dan integrasi `@google/genai`
     disiapkan sebagai roadmap lanjutan untuk asesmen kebutuhan lapangan cerdas.
