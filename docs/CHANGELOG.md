### Added
- **QA tambahan (regresi Fase 5 — akses user biasa)** *(Fase 6 lanjutan)*: `scripts/qa-phase6.ts` kini juga membuktikan user biasa BISA query baca `disasters` berstatus `admin_approved` (HTTP 200 — jalur `getDisasters('published')`) dan SEMUA panggilan REST memakai retry wrapper (`rafetch`) untuk toleransi jaringan ETIMEDOUT ke Google API. Catatan penting: REST Firestore `runQuery` harus memakai URL `.../documents:runQuery` dengan koleksi di body `from` — bentuk `.../disasters:runQuery` di-resolve sebagai `createDocument` (HTTP 400).
- **Audit Task 7 "Sinkronisasi Progres Kolektif"** *(Refactor Donasi Kolektif)*: audit menyeluruh pada sumber progres donasi — SEMUA tampilan progres (dashboard, katalog, halaman donasi, laporan akhir) membaca dari sumber kolektif server-side (`GET /api/fundraising/summary` via `useFundraisingSummary().getDisasterStats()` / `/report/:disasterId`); target bernilai global (`disasters.fundingTarget` → `FUNDRAISING_TARGET`), tidak pernah per-akun; agregasi server hanya menghitung donasi+payment `status === 'paid'` (pending/failed/expired otomatis terabaikan) tanpa counter materialized (read-time → tak mungkin dobel-hitungan, callback idempotent). Nilai per-akun yang tersisa (`UserDashboardOverview.totalUserDonation`, riwayat transaksi, total donatur partner) adalah statistik pribadi/administratif yang memang scoped per-akun. **Verifikasi live**: test baru di `scripts/qa-phase6.ts` — donasi `pending_payment` milik user QA **tidak** mengubah `collected`/`donationCount` bencana (butir 4 Task 7), ditambah uji identik antar-akun (butir 1/3/6) — SEMUA PASS; donasi uji otomatis dihapus setelah verifikasi.
- **QA sandbox 2 akun Firebase + sinkronisasi docs** *(Fase 6 — Refactor Donasi Kolektif)*: `scripts/qa-phase6.ts` membuat 2 akun pengguna QA via Admin SDK, membuktikan `GET /api/fundraising/summary` & `/report/:disasterId` **IDENTIK untuk guest = user A = user B** (bukti agregasi kolektif server-side), menguji rules LIVE (read timeline diizinkan; write timeline/earthquakeEvents/disasters **ditolak 403** utk pengguna biasa), lalu menghapus akun QA. Docs disinkronkan: `DATABASE.md` (schema + aturan write baru + koleksi `disasterTimeline` + `fundingTarget`/`archivedAt`), `CURRENT_STATE.md` (Phase 8).
- **Hardening `firestore.rules` (least privilege)** *(Fase 5)*: write `payments` & `donations` (create/update) dibatasi ke pemilik transaksi sendiri/admin/partner (jalur guest dihapus — checkout wajib login); `partnerAllocations`, `distributionReports`, `auditLogs` → admin/partner; `partners` → admin; `earthquakeEvents` → admin; `disasters` → admin/partner. Dukungan refactor **`POST /api/bmkg/refresh`** (auth: Firebase ID token sembarang pengguna) — tombol "Refresh BMKG" pengguna biasa kini mengingest via **server (Admin SDK)** sebagai `pending_verification` (tidak lagi menulis Firestore langsung dari browser). Read tetap role-scoped (transparansi/peran tidak berubah). Deploy: `firebase deploy --only firestore:rules --project bersamakita-app` (✓ 11 Okt 2026).
- **Laporan AKHIR per bencana + aksi "Tutup Penggalangan"** *(Fase 4 — Refactor Donasi Kolektif)*: `GET /api/fundraising/report/:disasterId` menghitung laporan final seluruhnya dari transaksi tercatat (donasi paid + fee, pencairan, alokasi, laporan distribusi, timeline) — transparan & tidak bisa dipalsukan. `POST /api/fundraising/admin/close` menutup penggalangan (status `archived` + audit + event timeline `fundraising_closed`) secara atomik & idempoten. UI: panel `AdminFinalReportPanel` di portal admin (tab Pencairan) dan `FinalReportSection` publik di layar "Penggalangan Ditutup" halaman donasi.
- **Timeline penyaluran KOLEKTIF per bencana** *(Fase 3 — Refactor Donasi Kolektif)*: koleksi `disasterTimeline/{disasterId}/events` — SATU timeline utk SEMUA donatur bencana yang sama (read publik tanpa PII, write admin/partner di `firestore.rules`). Komponen `DisasterTimelineSection` ditampilkan di dashboard bencana ("Lacak Bantuan — Timeline Penyaluran"); admin/partner dapat mempublikasikan update manual dari UI, dan event otomatis dibuat saat: pencairan diajukan (`disbursement_created`), mitra konfirmasi dana diterima (`funds_received_by_partner`), milestone penyaluran di-update (`milestone_updated`). Tracking per-donasi (`trackingEvents`) tetap ditulis sebagai nota privat donatur.
- **Pencairan kolektif dengan validasi saldo SERVER-SIDE** *(Fase 3)*: `POST /api/fundraising/admin/disbursements` (Auth: Firebase ID token + role admin) menghitung ulang saldo dari data nyata dan menulis disbursement + allocation (kolektif per bencana) + audit + timeline dalam SATU transaksi atomik (`runTransaction`). `DisbursementManager` kini memakai endpoint ini + recap dari `GET /api/fundraising/summary` (bukan state donations `limit(100)`). Alokasi **per-donasi** dihapus dari `PartnerDashboardView` (`handleStartDistributionFromDonation`) — pengelolaan penyaluran kini kolektif via pencairan admin.
- **Progres donasi KOLEKTIF per bencana di seluruh halaman publik** *(Fase 2 — Refactor Donasi Kolektif)*: `useFundraisingSummary` (hook) + `fetchFundraisingSummary()` (service) membaca `GET /api/fundraising/summary`. Dashboard (`WideDisasterDashboard`), Katalog BMKG (`DisasterList`), dan halaman donasi (`TransactionDonatePage`) kini menampilkan dana terkumpul/jumlah donatur/target **yang sama untuk semua akun** (guest/user/admin/partner) — tidak lagi dihitung dari donations milik user sendiri (fix inkonsistensi antar-akun Google). Target per bencana baru: `disasters.fundingTarget` (opsional, fallback Rp50jt).
- **`GET /api/fundraising/summary`** public endpoint (Firebase Admin SDK): sumber kebenaran progres donasi **kolektif per bencana** — identik untuk semua role. Agregasi server-side dari `donations`+`payments` berstatus `paid` (join `donationId`) dan `disbursements`, dengan semantik finansial yang sama dengan `DisbursementManager` (`collected`, `adminFeeTotal`, `donationCount`, `disbursed`, `inflight`, `remaining`, `fundingTarget`, `status`, `partnerName`). Anti-double-count inheren karena konfirmasi pembayaran idempotent. *(Fase 1 — Refactor Donasi Kolektif)*
- **Transparent 0,17% admin fee**: single source of truth in `src/lib/fees.ts` (`ADMIN_FEE_RATE`, `calculateAdminFee`, `calculateTotalPayment`, `MIN_WITHDRAWAL`) shared by frontend and backend. Fee is charged on top of the donation (`Total Dibayar = Donasi + Biaya Admin`), stored separately (`payments.fee`), and displayed on the donate page (with "Kenapa ada biaya admin?" explainer), on the checkout page, and in the public Riwayat Dana Masuk.
- **`GET /api/transparency/summary`** public endpoint (Firebase Admin SDK): riwayat dana masuk per donatur + total/biaya admin/per-bencana fundraising totals — identical data for every role without relaxing `firestore.rules`.
- **TransparencySummarySection** on the Transparansi Penyaluran page (topmost): "Riwayat Dana Masuk" (donatur, keterangan, waktu, donasi, biaya admin 0,17%, total, metode QRIS) and "Informasi Penggalangan Dana" (nama bencana, total terkumpul, jumlah donatur, riwayat transaksi dengan filter per bencana).
- Withdrawal transparency: `Disbursement` now records `fee` + `totalAmount`; the pencairan modal shows a live breakdown (Saldo Tersedia / Dana Ditarik / Biaya Admin 0,17% / Total Pengeluaran).

### Fixed
- **`POST /api/admin/create-partner` 403 "Forbidden: Admin access required" (Master Admin)**: allowlist admin di `server/routes/admin.ts` hanya memuat `admin_backend@bersamakita.org` + `contohasdf@gmail.com` (+ `users.role == 'admin'`), padahal `firestore.rules`/AuthContext/endpoint server lain sudah mengizinkan `bersamakita.my.id@protonmail.com` (master admin yang dipakai `loginStaff`). Akibatnya `create-partner` (satu-satunya endpoint admin yang belum memuat email master) menolak token master admin → admin tidak bisa menambah mitra lapangan dari dashboard. **Fix**: email master ditambahkan ke allowlist `create-partner`, selaras dengan `firestore.rules` + semua endpoint server lain. **Fix kedua (akar data)**: `subscribeAuthState` memanggil `syncUserProfile(fbUser, 'user')` sehingga role akun staf (admin/partner) di dokumen `users/{uid}` SELALU tertimpa menjadi `'user'` setiap sign-in/refresh (terkonfirmasi: `users.role` master admin = `user`). Kini ada helper terpusat `staffRoleForEmail()` (3 email admin + 1 email partner — satu sumber kebenaran, selaras `firestore.rules`), dipakai `syncUserProfile` (incl. `admin_backend@bersamakita.org`) dan `AuthContext` untuk mensinkronkan role yang BENAR per akun; akun Google biasa tetap dipaksa `'user'` (perilaku lama dipertahankan).
- **Regresi akses BMKG untuk pengguna biasa (user Google lain)**: semua jalur ingest BMKG yang tersisa di sisi klien — **bootstrap "Initial BMKG pool check"** (`loadData`, admin-gated) dan **`handleAdminRefreshBMKG`** — masih menulis `earthquakeEvents`/`disasters` langsung dari browser. Setelah hardening `firestore.rules` (Fase 5) write kolektif itu hanya diizinkan utk admin/partner, sehingga session dengan flag staff admin yang tersisa (`staffSession` stale) tetapi memakai token akun Google biasa memicu `FirebaseError: Missing or insufficient permissions` (write `disasters/...`), plus `getDisasters('all')` (query tanpa filter status → rules tak bisa membuktikan `isAdmin()` tanpa `get()`) ikut ditolak baca (403 terkonfirmasi via REST) — akibatnya daftar bencana user jadi kosong. **Perbaikan 2 lapis**: (1) `App.tsx` memakai satu helper server-side `refreshBMKGServer()` (`POST /api/bmkg/refresh` via Admin SDK) untuk pool check, tombol user refresh, DAN admin refresh — klien **tidak lagi menulis** ke `earthquakeEvents`/`disasters` di jalur mana pun; (2) `AuthContext` kini **merekonciliasi `staffSession` dengan Firebase user aktif** (jika email session staff ≠ email token aktif, session dibersihkan) sehingga mismatch "flag admin stale + token non-admin" tidak terjadi lagi; ditambah fallback `getDisasters('published')` di `loadData` bila query admin `'all'` gagal. QA baru membuktikan user biasa tetap bisa membaca disaster `admin_approved` (HTTP 200).
- **`Access to storage is not allowed from this context.`**: `getStorage(app)` dieksekusi saat import `src/config/firebase.ts` dan melempar error runtime di konteks tanpa `indexedDB` (iframe/sandbox/preview). Tidak ada modul yang mengimpor `storage` (semua upload bukti penyaluran via Cloudinary/server), jadi inisialisasi Storage kini **dihapus**; bila kelak dibutuhkan, inisialisasi lazy di modul pemakainya.
- **Disbursement balance check now includes the admin fee everywhere**: the "Buat Pengajuan Pencairan" gate and its hint now require `saldo ≥ MIN_WITHDRAWAL + biaya admin` (`MIN_WITHDRAWAL_TOTAL`, e.g. Rp1.000.000 + Rp1.700 = Rp1.001.700) instead of comparing the saldo with the nominal only, and the input's "Maksimal" hint shows `maxWithdrawableAmount(remaining)` (largest nominal whose nominal + fee still fits the remaining cash) instead of the raw remaining balance. Submit-time validation continues to compare `nominal + biaya admin` against the disaster's remaining cash.
- `payments` documents now store `userId`, so `firestore.rules` grants owners read access — checkout no longer shows "Transaksi Tidak Ditemukan" for regular users.
- `simulate-paid` / `expire-sweep` now record `paidAmount = amount + fee` (they previously wrote the nominal only once a fee existed).
- Status page receipt label clarified to "Nominal Donasi".
